# Order draft storage setup

The order page intentionally creates `draft` records only. It does not confirm a print-ready job, expose customer details, or start payment.

## Supabase setup

1. Select the **`amuhon-staging`** Supabase project. Do not use the production `amuhon` project for setup or tests.
2. Apply `supabase/migrations/20261017000100_order_drafts.sql` and then `supabase/migrations/20261020000100_order_asset_uploads.sql` to that staging project using the Supabase migration workflow. The second migration is additive; it does not change the existing order migration.
3. For local development, configure these server-only variables in `.env.local`; for deployment, configure them in that environment's secret-variable settings. Obtain the URL and key only from the selected `amuhon-staging` project's Dashboard:
   - `SUPABASE_URL`: the staging project URL. Find it in the project's **Connect** dialog or **Project Settings → API**.
   - `SUPABASE_SERVICE_ROLE_KEY`: the staging project's server-side service-role/secret key, from **Project Settings → API Keys**. The current API route expects this environment-variable name. Never use a `NEXT_PUBLIC_` name or expose the value to browser code.
   - `ORDER_RATE_LIMIT_SECRET`: a long random secret used to HMAC the trusted client address before storing its rate-limit key.
   - `ORDER_APP_ORIGIN`: canonical application origin, e.g. `http://localhost:3000` locally or `https://your-staging-domain.example` in staging (set it when reverse-proxy URL forwarding differs).
   - `ORDER_DRAFT_RETENTION_DAYS`: optional integer from 1 through 365; defaults to 30.
   - `ORDER_UPLOAD_CLEANUP_SECRET`: a separate random secret of at least 32 characters for the scheduled stale-upload cleanup route. Do not reuse the rate-limit secret.
4. Before saving the variables, verify that both URL and key are shown under **`amuhon-staging`** in the Dashboard. Do not copy either from `amuhon`.
5. Configure the ingress proxy to overwrite `X-Real-IP` or the first `X-Forwarded-For` address. The app hashes the selected address and never writes the raw address to the database or logs. Without a trusted client address the API refuses to save.
6. Schedule a server-side call to `purge_expired_amuhon_order_drafts()` at an interval appropriate for the configured retention. The migration sets draft expiry; it does not create a scheduler.

The migrations enable row-level security and grant no direct table access to browser or service REST roles. Their `SECURITY DEFINER` RPCs retain the Supabase-managed `postgres` owner, use a restricted `search_path`, and grant execution only to `service_role`; no custom executor role is created. The second migration stores only a SHA-256 hash of a 256-bit upload capability, provides short upload leases and an independent hashed-IP upload rate limit, and records verified file checksums and paths. It reuses the private `amuhon-order-files` bucket, whose browser-role deny policy remains in force. Server-side Storage calls use the service-role credential; the browser never receives it.

The `/order` confirmation step requires the user to select the body-only A6 PDF and the spread-cover PNG previously downloaded from `/final` and `/cover`. The server ignores the filenames and multipart MIME labels, parses the actual PDF page count and A6 MediaBox/CropBox, decodes the PNG, verifies its pixel dimensions and 350dpi metadata, and compares the actual PDF count with the draft declaration when one exists. A successful upload stores the deterministic private object paths and checksums on the order, and leaves its status at `preparing`; price remains unset, so it cannot become payable. The server associates the two files with the order capability and validates the print metadata, but it does not extract/compare every PDF text glyph against the selected works list.

Each asset is limited to 60MiB; the multipart request is capped at approximately 120MiB. The route uses the Node.js runtime and declares a 120-second maximum. This is only an application-level limit: the deployment ingress must also accept requests of that size and the hosting plan must allow the route duration and sufficient memory. The README describes Vercel as a deployment option, but Vercel Functions currently enforce a 4.5MB request/response payload limit, so this server-proxied upload route cannot accept the documented files there. Before deploying this upload path to Vercel, redesign it around a capability-authorized direct-to-private-Storage upload or use an ingress that supports the full request size. Other hosts must be checked against their current ingress, duration, and memory limits; `maxDuration` does not configure the request-body limit.

Storage uploads use fixed per-order object keys. The API tries to delete both keys and release its lease if a write or finalization fails. To recover from a process crash or a failed compensating delete, schedule an authenticated `POST /api/internal/cleanup-order-uploads` with `Authorization: Bearer <ORDER_UPLOAD_CLEANUP_SECRET>` (for example, every 10–15 minutes). The cleaner only claims stale, unvalidated `preparing` orders, deletes their two deterministic objects, and releases the lease; a crash during cleanup is retried after its lease expires. It returns counts only and does not expose customer data.

The database rate limiter allows five new draft submissions per hashed client address per 15-minute window. Retries with the same idempotency key return the existing safe order identifier and status without incrementing the counter. Expired rate-limit hashes are pruned opportunistically after 24 hours. Run `supabase/tests/order_drafts.test.sql` only against the intended non-production staging project after verifying its project reference; the test includes an explicit staging confirmation guard and rolls back its test transaction. It checks grants, function owner attributes, constraints, idempotency, and rate limiting.

## Current boundaries

Files must still be generated and downloaded in the browser, then selected in `/order`; the application does not yet produce a server-side PDF or automatically prove that all text in a supplied PDF came from the selected works. `declared_body_pdf_page_count` remains an untrusted review hint; the server-derived PDF count is authoritative and must match the hint when present. Database constraints prevent a row from entering `ready_for_payment` without server-verified paths, a validation timestamp, final page count, and finalized price. No customer-information read/list route exists.

Before real orders, configure the cleanup scheduler, implement authorized administrative access, price calculation, a secure customer-data retention/deletion job, and operational monitoring. Apply and test both migrations and RPCs only against a non-production Supabase project before deployment.
