# Order draft storage setup

The order page intentionally creates `draft` records only. It does not confirm a print-ready job, expose customer details, or start payment.

## Supabase setup

1. Select the **`amuhon-staging`** Supabase project. Do not use the production `amuhon` project for setup or tests.
2. Apply `supabase/migrations/20261017000100_order_drafts.sql`, `supabase/migrations/20261020000100_order_asset_uploads.sql`, and `supabase/migrations/20261020000200_order_asset_size_limit.sql` in order. The temporary direct-upload experiment additionally requires `supabase/migrations/20261020000300_order_temp_uploads.sql`. All migrations after the first are additive; this experiment does not edit the existing migrations or move existing objects.
3. For local development, configure these server-only variables in `.env.local`; for deployment, configure them in that environment's secret-variable settings. Obtain the URL and key only from the selected `amuhon-staging` project's Dashboard:
   - `SUPABASE_URL`: the staging project URL. Find it in the project's **Connect** dialog or **Project Settings → API**.
   - `SUPABASE_SERVICE_ROLE_KEY`: the staging project's server-side service-role/secret key, from **Project Settings → API Keys**. The current API route expects this environment-variable name. Never use a `NEXT_PUBLIC_` name or expose the value to browser code.
   - `ORDER_RATE_LIMIT_SECRET`: a long random secret used to HMAC the trusted client address before storing its rate-limit key.
   - `ORDER_APP_ORIGIN`: canonical application origin, e.g. `http://localhost:3000` locally or `https://your-staging-domain.example` in staging (set it when reverse-proxy URL forwarding differs).
   - `ORDER_DRAFT_RETENTION_DAYS`: optional integer from 1 through 365; defaults to 30.
   - `ORDER_UPLOAD_CLEANUP_SECRET`: a separate random secret of at least 32 characters for the scheduled stale-upload cleanup route. Do not reuse the rate-limit secret.
   - `NEXT_PUBLIC_SUPABASE_ANON_KEY`: only the staging project's publishable/anon key, used by the browser TUS client. This is a public key; never put a service-role/secret key under this name.
   - `NEXT_PUBLIC_ORDER_DIRECT_UPLOAD_EXPERIMENT`: leave unset or set to `false` by default. Set to `true` only in a staging preview after the temporary-bucket migration and public anon key are configured.
   - `NEXT_PUBLIC_ORDER_UPLOAD_DIAGNOSTICS`: temporary TUS-auth troubleshooting only. Leave unset or `false` normally; for local development, set to `true` alongside `NEXT_PUBLIC_ORDER_DIRECT_UPLOAD_EXPERIMENT=true`, then restart `npm run dev`. The API and UI additionally require `NODE_ENV=development`; production never returns or renders diagnostic results. The diagnostic panel reports booleans only (exact signature/header match, non-empty/three-part shape, public `apikey` match, and signer/TUS project match). It does not log or display credential values. Remove this flag and the isolated diagnostic code after the investigation.
   - `ORDER_TEMP_UPLOAD_CLEANUP_ENABLED`: server-only `true` in an environment that has applied the temporary upload migration and needs abandoned temporary objects purged. Keep enabled while temporary attempts may exist, even if the UI experiment flag is later turned off.
4. Before saving the variables, verify that both URL and key are shown under **`amuhon-staging`** in the Dashboard. Do not copy either from `amuhon`.
5. Configure the ingress proxy to overwrite `X-Real-IP` or the first `X-Forwarded-For` address. The app hashes the selected address and never writes the raw address to the database or logs. Without a trusted client address the API refuses to save.
6. Schedule a server-side call to `purge_expired_amuhon_order_drafts()` at an interval appropriate for the configured retention. The migration sets draft expiry; it does not create a scheduler.

The migrations enable row-level security and grant no direct table access to browser or service REST roles. Their `SECURITY DEFINER` RPCs retain the Supabase-managed `postgres` owner, use a restricted `search_path`, and grant execution only to `service_role`; no custom executor role is created. The second migration stores only a SHA-256 hash of a 256-bit upload capability, provides short upload leases and an independent hashed-IP upload rate limit, and records verified file checksums and paths. It reuses the private `amuhon-order-files` bucket, whose browser-role deny policy remains in force. Server-side Storage calls use the service-role credential; the browser never receives it.

The `/order` confirmation step requires the user to select the body-only A6 PDF and the spread-cover PNG previously downloaded from `/final` and `/cover`. In the existing mode, the server ignores filenames and multipart MIME labels, parses actual file metadata, and stores verified files in the final private bucket. In the disabled-by-default direct-upload experiment, the server instead authorizes temporary Storage uploads only; it does not parse, verify, promote, or finalize them. Temporary-upload success leaves the order in `preparing` with `files_validated_at`, final object paths, and checksums unset. It never makes the order payable.

The order upload capability is generated server-side as 256 random bits; only its SHA-256 hash is stored in the database. The raw capability is set as a host-only `HttpOnly; SameSite=Strict` cookie scoped to `/api/orders/{orderId}` (and `Secure` in production) and is no longer returned in JSON. The direct-intent endpoint requires this cookie, exact `Origin`, a valid order state, and the existing rate-limit/lease RPC. An order ID alone is insufficient. The browser receives only two short-lived signed upload tokens, each scoped to a unique attempt-specific temporary object key, plus the public anon key needed for TUS. The service-role key and order capability are never sent to browser JavaScript. Do not log intent response bodies or signed upload tokens.

For the experiment, enable `NEXT_PUBLIC_ORDER_DIRECT_UPLOAD_EXPERIMENT=true` only in a staging build/runtime after applying migration `20261020000300_order_temp_uploads.sql`. Supabase TUS uses 6 MiB chunks, retry backoff, and `tus-js-client`'s browser upload URL store for resume. Retry from the same browser with the same order and files; a new attempt ID gets different object keys. This first stage does not offer a server-authorized “replace” operation. Signed upload tokens and resumable sessions expire; abandoned temporary objects are eligible for cleanup after 26 hours. Schedule the authenticated temporary cleaner and set `ORDER_TEMP_UPLOAD_CLEANUP_ENABLED=true`; it uses service-role server-side deletes against only validated attempt-specific paths. The server-side cleanup flag is independent of the UI experiment flag so disabling new uploads does not strand old temporary objects.

Supabase's TUS endpoint, signed-token header behavior, bucket policy interaction, CORS, and end-to-end pause/resume must be verified in `amuhon-staging` after the migration is applied. This implementation has not connected to Supabase or exercised a real TUS transfer. Supabase documents resumable uploads and signed upload tokens; no Storage operation is performed during local tests.

Each asset is limited to exactly 40,000,000 bytes (40 MB, decimal); the multipart request is capped at 80,131,072 bytes (two files plus 128 KiB for multipart framing). The private Storage bucket limit is also set to 40,000,000 bytes by the additive migration `20261020000200_order_asset_size_limit.sql`; apply that migration to each Supabase environment before relying on the bucket-level guard. This stays below the Supabase Free project-wide file cap of 50 MB, but the project plan and current Dashboard setting must still be checked. The route uses the Node.js runtime and declares a 120-second maximum. This is only an application-level limit: the deployment ingress must also accept requests of that size and the hosting plan must allow the route duration and sufficient memory. The README describes Vercel as a deployment option, but Vercel Functions currently enforce a 4.5MB request/response payload limit, so this server-proxied upload route cannot accept the documented files there. Before deploying this upload path to Vercel, redesign it around a capability-authorized direct-to-private-Storage upload or use an ingress that supports the full request size. Other hosts must be checked against their current ingress, duration, and memory limits; `maxDuration` does not configure the request-body limit.

Legacy final Storage uploads use fixed per-order object keys. The API tries to delete both keys and release its lease if a write or finalization fails. To recover from a process crash or a failed compensating delete, schedule an authenticated `POST /api/internal/cleanup-order-uploads` with `Authorization: Bearer <ORDER_UPLOAD_CLEANUP_SECRET>` (for example, every 10–15 minutes). The legacy cleaner remains unchanged. When temporary cleanup is enabled, schedule a separate authenticated `POST /api/internal/cleanup-order-temp-uploads` with the same cleanup secret. It claims at most two expired attempts per invocation, validates every returned key against its order and attempt UUID, deletes only those exact temporary paths, and records cleanup success/failure. A crash during cleanup is retried after the cleanup lease expires. Neither endpoint exposes customer data.

The database rate limiter allows five new draft submissions per hashed client address per 15-minute window. Retries with the same idempotency key return the existing safe order identifier and status without incrementing the counter. Expired rate-limit hashes are pruned opportunistically after 24 hours. Run `supabase/tests/order_drafts.test.sql` only against the intended non-production staging project after verifying its project reference; the test includes an explicit staging confirmation guard and rolls back its test transaction. It checks grants, function owner attributes, constraints, idempotency, and rate limiting.

## Current boundaries

Files must still be generated and downloaded in the browser, then selected in `/order`; the application does not yet produce a server-side PDF or automatically prove that all text in a supplied PDF came from the selected works. In the direct-upload experiment, files are temporary and unverified, so the UI explicitly does not show “verified” completion. `declared_body_pdf_page_count` remains an untrusted review hint; the legacy server-derived PDF count is authoritative and must match the hint when present. Database constraints prevent a row from entering `ready_for_payment` without server-verified paths, a validation timestamp, final page count, and finalized price. No customer-information read/list route exists.

Before real orders, configure the cleanup scheduler, implement authorized administrative access, a secure customer-data retention/deletion job, and operational monitoring. Apply and test migrations and RPCs only against a non-production Supabase project before deployment.

## Beta Stripe Checkout (test mode only)

The additive migration `supabase/migrations/20261103000100_order_stripe_checkout.sql` adds server-only checkout RPCs and a minimal webhook idempotency ledger. It must be separately reviewed and applied after the existing order, asset-finalization, and validation migrations; this repository change does not apply it to any Supabase project. The existing final-file upload RPC continues to leave orders in `preparing`. Only the new checkout RPC can move an order to `ready_for_payment`, and it derives the JPY total from the server-verified PDF page count while holding the order row lock. Unsupported page counts (under 24 or over 300), missing verified assets, declared/verified page-count mismatch, and a stored-price mismatch all stop checkout. The configured amounts are ¥1,980 / ¥2,280 / ¥2,580 / ¥2,880 / ¥3,180 for 24–100 / 101–150 / 151–200 / 201–250 / 251–300 pages. `amount_minor` stores the total number of JPY, including tax and shipping; `shipping_minor` is zero because shipping is bundled into that total.

The checkout API accepts no client amount. It requires the existing HttpOnly order upload capability and exact request Origin, uses only a server-side `STRIPE_SECRET_KEY` beginning with `sk_test_`, explicitly enables card-only Checkout, and stores/reuses one idempotent session per order. It does not automatically replace an expired or uncertain session: such an order requires manual reconciliation before another session is created. Configure `ORDER_APP_ORIGIN` to the single canonical application origin. Never set a live Stripe key for this beta. The success redirect is informational only; it never changes payment state.

The webhook route requires `STRIPE_WEBHOOK_SECRET` (`whsec_...`) and validates the timestamped signature over the raw request body. It handles only a signed, test-mode, paid `checkout.session.completed` event. The database RPC compares the order, checkout attempt, session, amount, currency, and payment-intent ID under a row lock, then records the payment and event ID atomically. Repeated Stripe deliveries are idempotent. Do not register an external webhook or run a real payment as part of this code change. Before enabling Checkout in a deployed test environment, separately apply/review the migration, configure only Stripe test-mode secrets, register a test endpoint with Stripe, and exercise card test numbers. None of those external setup steps has been performed here.

The new `/order/success` and `/order/cancel` pages read status through the order capability cookie. The `session_id` query parameter is not used as proof of payment. A canceled Checkout session can be reopened through the same server-side idempotent session; if that session expired, the server refuses automatic replacement to avoid overlapping payment sessions.

## Operator order management

The operator pages are `/admin/login`, `/admin`, and `/admin/orders/{order-id}`. Login uses Supabase Auth email/password through the official `@supabase/ssr` cookie client. There is no sign-up page or public account-creation endpoint. The login session is not itself administrator permission: every admin page/API calls server-side `auth.getClaims()` and compares the verified `sub` UUID with the single server-only `AMUHON_ADMIN_USER_ID`. Missing or malformed IDs disable access (503); a different valid user ID is denied (403). Email address and client-supplied flags are never used as the administrator identity.

Required environment configuration:

- `SUPABASE_URL`: server-side Supabase project URL already used by order APIs.
- `NEXT_PUBLIC_SUPABASE_URL`: the same project URL for the Auth browser client.
- `NEXT_PUBLIC_SUPABASE_ANON_KEY`: the public anon/publishable key used by the existing browser upload flow and Auth client. This is not a service-role key.
- `SUPABASE_SERVICE_ROLE_KEY`: server-only key used by admin APIs only after the Supabase Auth subject passes the allowlist check. Never use a `NEXT_PUBLIC_` name.
- `AMUHON_ADMIN_USER_ID`: server-only UUID of the one operator's Supabase Auth user. Leave unset until the operator account exists; admin pages and APIs then fail closed.
- `ORDER_APP_ORIGIN`: exact canonical app origin; required for the manual-submission state-change request.

Create the operator account through the Supabase Dashboard's Auth user management, not through this app. Copy that account's `user.id` UUID into the server environment as `AMUHON_ADMIN_USER_ID`, then deploy/restart the server. Do not use an email address in this setting. Keep Supabase Auth public sign-ups disabled in project settings; no registration flow is included here. The browser receives only the public anon key; `SUPABASE_SERVICE_ROLE_KEY` and `AMUHON_ADMIN_USER_ID` are never passed to client components.

The admin list/detail and file APIs use service-role-only SECURITY DEFINER RPCs after server authorization. The file endpoint returns a no-store attachment only for a `paid` order whose finalized object paths, SHA-256 values, and file-validation timestamp match an approved deterministic private-bucket path. It supports the legacy per-order keys and the validation-worker's attempt-specific keys, downloads the exact path returned by the guarded RPC through the server, rejects redirects, enforces the 40,000,000-byte cap, and hashes the bytes again; it does not expose signed or public Storage URLs. The manual printer state is separate from payment status. Its row-locked RPC allows only paid orders with verified files, records the authenticated administrator UUID, and treats repeated submissions idempotently.

Migration `20261103000200_order_admin_fulfillment.sql` adds the separate fulfillment state and four service-role-only RPCs. It has **not** been applied. No Supabase project was accessed, no Auth login was performed, no real Storage file was downloaded, no order state was changed, and no printer submission occurred. Before production use, review and apply the checkout and admin migrations in the intended non-production project, create the operator Auth account, configure the server variables, and test with synthetic/test-mode data. Define customer-data retention/deletion, refund/cancel handling, and manual order reconciliation before accepting a real beta order.

## Validation-job SQL tests

The SQL tests are split by scope:

- `supabase/tests/order_validation_jobs.test.sql` exercises the **global** `claim_amuhon_order_validation_job` RPC. **Do not run this test against shared staging or production.** Its precheck can detect currently claimable jobs, but cannot eliminate a race with a concurrent enqueue/worker; the global RPC could claim and mutate an unrelated job. Use only a dedicated isolated database with no concurrent writers. It avoids the global cleanup and rate-limit-pruning RPCs and rolls back its synthetic rows, but `ROLLBACK` cannot undo a claim made against another transaction's job.
- `supabase/tests/order_validation_targeted_claim.test.sql` exercises only the new exact-order/exact-attempt claim RPC. It creates synthetic rows with random IDs directly inside one `READ COMMITTED` transaction, never calls the global claim or cleanup RPC, performs no Storage I/O, and ends with `ROLLBACK`. It is designed for manual staging verification after the targeted-claim migration is separately reviewed and applied. Confirm the Dashboard project is `amuhon-staging`, replace the confirmation sentinel, and run as `postgres`. The test checks sequential double-claim and no-fallback behavior; it does not simulate truly concurrent sessions. If an error stops execution before the final `ROLLBACK`, run `ROLLBACK` in that SQL Editor session before closing it.
- `supabase/tests/order_validation_jobs_cleanup.isolated.sql` exercises the global temp-file cleanup RPC. It is **only for a dedicated empty isolated database**, never shared staging or production. Its empty-table precondition is intended to fail closed, but does not identify the Supabase project or prevent concurrent writes. Do not run it while any application, worker, or cleanup scheduler can create or claim attempts. It invokes only database RPCs and does not delete Storage objects; it simulates cleanup outcomes by updating synthetic rows inside a transaction that is rolled back.

The staging status may include expired `issued` attempts. The targeted-claim staging test does not search for or lock those attempts because it passes freshly generated order and attempt IDs directly. Do not bypass the isolated cleanup test's empty-database guard to test cleanup on shared staging.

## Targeted validation claim (not applied)

`supabase/migrations/20261025000100_order_validation_targeted_claim.sql` is an additive migration. It preserves the signature and return type of the global `claim_amuhon_order_validation_job(integer)` and adds the `declaredPageCount` JSON key, including JSON `null` when the order has no declared count. It also adds `claim_amuhon_order_validation_job_for_attempt(uuid, uuid, integer)`, which can only claim the supplied order/attempt pair and returns `null` when that exact pair is missing, locked, or not claimable; it never falls back to another job. Both functions use `SECURITY DEFINER`, fixed `search_path`, and service-role-only EXECUTE grants. Both lock in `order → attempt → job` order, then revalidate that the order is `preparing`, unfinalized, and has an active upload lease matching the attempt lease. The returned job lease is capped by both the attempt and order upload-lease expiries. Existing attempt expiry and five-attempt rules remain in force. When the order/attempt is no longer eligible, the job is marked terminally failed with `attempt_expired` so the global queue does not repeatedly select it.

 This migration has **not** been applied or tested against Supabase by Codex. The existing SQL test `supabase/tests/order_validation_jobs.test.sql` invokes the global claim and must not be run on shared staging; the new targeted-claim SQL test does not invoke it. The targeted test's sequential checks do not prove behavior under simultaneous database sessions. The worker adapter now exposes only the exact-target claim operation, and `runOnce({ orderId, attemptId })` requires both identifiers; the adapter and worker reject a returned target mismatch before any Storage operation. A future manual runner should accept both UUIDs explicitly from a trusted operator-controlled input and invoke this exact-target interface; do not expose a service-role-backed invocation to the browser. There is still no CLI, API route, scheduled task, or other worker entry point, so this change does not start processing. Candidate discovery is non-locking; after discovery, both claim functions lock order, attempt, then job and recheck eligibility under those locks. Attempt-first fail/retry/cleanup paths use `SKIP LOCKED` from claim, so they are skipped rather than waited on while the order lock is held.

## Atomic validation asset commit (not applied)

`supabase/migrations/20261022000100_order_validation_asset_commit.sql` adds the atomic finalization RPC and updates the validation-only `complete_amuhon_order_validation_job` RPC so it can no longer mark a job successful by itself. The new `commit_amuhon_order_validation_assets` RPC records the attempt-specific final paths, verified PDF page count, SHA-256 strings, byte sizes, and `files_validated_at` together with `state='succeeded'`, in one PostgreSQL transaction. It leaves the order in `preparing` and does not set price, currency, or Stripe fields. The migration also changes temp-attempt cleanup eligibility: a succeeded job is eligible only after the order row references both exact attempt-specific final keys and matching verified metadata.

This migration has **not been applied or tested against Supabase by Codex**. Do not apply it until it receives a separate SQL review and the applied staging definitions are reconciled with the repository. Its SQL test, `supabase/tests/order_validation_asset_commit.test.sql`, uses synthetic UUIDs, does no Storage I/O, and rolls back its database changes. Before any manual run, confirm the Dashboard is on `amuhon-staging`, pause workers and cleanup schedulers, and replace the test's `CHANGE_THIS_TO_CONFIRM_amuhon-staging` sentinel with `amuhon-staging`. That sentinel is a manual confirmation gate; SQL Editor does not provide a reliable project-identity check in this test. Run as `postgres` at `READ COMMITTED`. A successful SQL test only verifies database behavior; it does not verify the existence or bytes of Storage objects.

The RPC checks that SHA-256 values have 64 lowercase hexadecimal characters and that the supplied keys match the fixed order/attempt format. It cannot inspect Storage contents. A trusted worker must independently validate the files, verify the exact bytes saved to the final bucket, and only then call the RPC. Storage writes and the database transaction are not atomic: partial or orphan final objects may remain after a failed save or uncertain commit. Keep those objects until an audited reconciliation process confirms whether the database references them; this migration does not delete final objects.
